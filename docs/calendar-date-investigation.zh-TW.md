# 12/1 參訪日期與 AGY effort 調查

調查基準：`bee904faf49f40ff9474c3f9a0d6a221367f05c3`（main）。

## 信件日期的傳遞路徑

1. `outlook_monitor._snapshot()` 讀取 `Body` 和 `ReceivedTime`，放進 `MailSnapshot`。
2. `ai._mail_data()` 把本文、主旨、`received_at` 等欄位組成 JSON。本文上限 60,000 字；長信在 Outlook 讀取階段會加截斷標記。
3. `ai.build_prompt()` 在**同一次請求**要求摘要與 `events`。Codex 與 AGY 共用這個 prompt；AGY 另加輸出協定規則。沒有把摘要另送到「加入行事曆」的 prompt。
4. `Analysis.from_dict()` 保留模型回傳的 `start`、`end`。確認視窗讀取這些欄位；`calendar_api.create_event()` 直接組成 Google Calendar payload，沒有再請 AI 判斷日期。

因此，截圖開頭的 `12/1` 與下方議程在正常讀取、未超過長度上限時，會一起送給模型。現有程式不支持「行事曆另一次 prompt 漏傳 12/1」這個假說。

## 已確認的問題與未確認事項

- 舊 prompt 只有「相對日期優先以 received_at 為基準」，沒有明說 `12/1` 省略年份如何推定，也沒有提醒將前言日期與下方議程合併讀取。這是判讀規則的缺口，並不能單憑程式碼證明是哪個模型失敗的唯一原因。
- 舊確認視窗只有在 `start` **與** `end` 同時存在時才預填。模型若只確認開始時間、未確認結束時間，視窗會把已知開始時間也顯示成空白。這個顯示問題已用回歸測試重現。
- 截圖中的「收信日期未提供」是 AI 產生的備註，不足以證明實際 `received_at` 為空。舊程式確實會在 `ReceivedTime` 讀取或轉換失敗時默默傳空字串；未取得原始 snapshot／CLI 結果前，無法確認該信是否經過這條路徑。
- 本次沒有使用使用者的 Outlook、原始郵件或 AGY 登入執行實測，亦未取得當時的 CLI JSON，不能從截圖斷定原本 `start`、`end` 的實際值。

## 修改

- 明確要求按收信日期與上下文判定省略年份的月日，處理明確跨年活動，並合併前言與議程表。`2026-11-11` 收到的 `12/1(二)` 在本案例應判為 `2026-12-01`。
- 分別保留已知的開始、結束時間；確認視窗也分別預填。未知結束時間仍留白並要求確認，不能以出發時間冒充抵達時間，也不能任意補會議長度。
- `ReceivedTime` 不可用時，以唯讀 MAPI `PR_MESSAGE_DELIVERY_TIME` 作備援，按 UTC 解讀；兩者都不可用時仍傳空字串，不填入目前日期。
- AGY effort 欄位反灰，以模型 ID 結尾的 `low / medium / high / xhigh / max` 同步顯示、儲存及執行參數。預設或不含已知後綴的模型不送 `--effort`，交由 CLI 依模型決定。舊設定不匹配也會在載入及建立命令時修正。

## 驗證範圍

使用去除身分資料、依截圖轉錄的議程 fixture，驗證 Outlook snapshot 到 Codex／AGY 請求仍包含完整本文與收信日期，以及模型回傳的單邊時間不會在解析時遺失。另測試日期備援、單邊時間預填、未知時間禁止新增、AGY 模型切換／手動輸入／清單重載／舊設定修復。這些測試的模型回應為 fixture，**不代表已驗證真實模型的日期推理品質**。

Windows 人工驗證方式：重新啟動更新後的程式並重新產生該信摘要，檢查開始日期應為 `2026-12-01`、開始時間為 `09:00`；結束時間依原文能否確認返回時刻決定。切換 AGY medium/high 模型，確認 effort 反灰且同步。若仍出現空白，需在使用者同意下本機比對去識別的 snapshot 與 CLI `events`，才能判定是輸入讀取、模型輸出或顯示問題；不應把完整私人郵件寫進一般記錄。
